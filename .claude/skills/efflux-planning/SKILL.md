# efflux-planning

Produce a wave-structured plan that `/efflux-executing` runs. The stack is fixed and known — do NOT run a detection dance (no probing for lint configs, test runners, or package managers). Bake decisions on the facts below and spend the planning budget on the actual task.

This is v1 of the skill — deliberately lean. It gets sharpened by `/efflux-postmortem` findings over future PRs.

## Stack (fixed)

- **Runtime/PM:** Bun workspaces — `apps/api` (Cloudflare Worker: HttpApi + `Agent` DO-per-session + Container sandbox), `apps/web` (Vite + React chat FE), `packages/shared` (HttpApi contract + schemas; all types flow from Effect Schemas).
- **Verify:** `bun run typecheck` (chains `bun run cf-typegen` first, regenerating the gitignored `worker-configuration.d.ts`, then the three tsconfigs), `bun run build`. `bun run test` (root vitest) and `bun run lint` (`biome check .`) ALSO exist and are CI-gated (`.github/workflows/ci.yml`: typecheck + test + lint, `--frozen-lockfile`). The `/efflux-executing` wave gate is typecheck-ONLY, so every plan MUST carry a pre-PR step that runs `bun run lint` + `bun run test` from the worktree (and commits an updated `bun.lock` on any dep change) — else the PR reds in CI while the waves looked green. **FE/tooling gotchas:** biome lints `apps/**`, so generated shadcn `components/ui/*` must be added to `biome.json` `files.includes` as `!` negations (they ship `!`/`as`), Tailwind-v4 CSS (`@theme`/`@apply`/`@custom-variant`) must be excluded from biome's CSS parser (add a `!<file>.css` negation), and inline `<script>` in `index.html` IS linted (use `const` + optional `catch`, never `var`). Any skill/agent file a plan creates must be committed on the plan's branch — files authored in the main checkout do not self-track into the worktree.
- **Deploy:** `bun run deploy` — ALWAYS the package script, never bare `wrangler deploy`: only the script fires the `predeploy` hook (FE build + skills upload), so the bare form can ship a stale `apps/web/dist`. Requires a local Docker daemon (container image). Local dev: `bun run dev` (also needs Docker). Logs: `bun run tail`. Treat the repo `CLAUDE.md` "Commands" section as the command authority. **Any task that verifies a FE surface locally MUST bake in two worktree gotchas (full detail in `/efflux-verifying`):** build `apps/web/dist` with `.dev.vars` sourced (`set -a; . .dev.vars; set +a; bun run build`) so `VITE_API_TOKEN` is inlined — a plain `bun run build` ships an empty token and every panel 401s; and start `wrangler dev` via the worktree's OWN `node_modules/.bin/wrangler --config <abs>/wrangler.jsonc` on free ports, never `bunx wrangler` (which can silently serve a SIBLING worktree's code, so new routes 404 and edits don't take effect).
- **Live smoke CLI:** `bun scripts/agent.ts <name> <id> --message "hi" [--url <worker-url>] [--model M] [--skill S] [--role R]` (or `BASE_URL` env).
- **Demo model pin:** any plan step that exercises the toolkit live (a tool loop) MUST pin `--model openai/gpt-4o-mini`. Never `openai/gpt-5.2` — it 400s the whole toolkit with a strict-schema error (ALL tools, not just new ones; the README uses gpt-5.2 only on the toolkit-free `/tasks` surface). Never rely on the free default `tencent/hy3:free`, which flakes at tool choice.
- **Conventions:** feature PRs target `staging` and use `Refs #N` (issues close only via `/efflux-releasing`'s staging→main promotion PR, which carries the `Closes #N` lines); merge commits only (never rebase/squash); never `--no-verify`; no `as` casts or `!` assertions; schema-first — types flow from Effect Schemas; verification means exercising a running worker, not typecheck/build alone — but LOCAL (`bun run dev`) is the default per `/efflux-verifying`, with the shared deployed worker reserved for a single final pre-PR pass (every deploy is real, billed Container usage). Code style: **JSDoc on declarations only — no inline `//` comments** (self-documenting code; fold only critical invariants into a declaration's JSDoc — ISSUES.md holds the deep gotchas); **files stay single-purpose** — split a new driver/subsystem into its own module rather than growing a file past ~400 lines. Inlined code shapes in task bodies MUST follow this (JSDoc-only, no `//`) so agents reproduce the house style — AND must themselves pass the no-`as`/no-`!` compliance grep `/efflux-executing` runs: NO `as const` in a plan's code block (use an explicit `ReadonlyArray<…>` / `readonly [...]` annotation instead), or the task agent has to strip it mid-wave (dev-local-command #115: an inlined `const X = [...] as const` was correctly removed by the executor's self-audit — the plan shipped a violation of the rule it enforces).
- **Plans dir:** `~/c0de/plans/efflux/`.
- **Execution model:** `/efflux-executing` runs the plan in an isolated worktree (`.claude/worktrees/<plan-name>`, branched from `origin/staging`) and spawns each wave's tasks as PARALLEL `efflux-task-executor` agents. Consequences for the plan: the `> **Branch:**` metadata line is REQUIRED (optionally `> **Base:**` when the work builds on an open PR branch instead of `staging`); no two tasks in the same wave may touch the same file (they run concurrently); and each task body must be SELF-CONTAINED — sub-agents reliably read their prompt but unreliably read referenced files, so inline any binding pattern or `**Do not:**` list into the task body rather than pointing at another document. **Every wave must also end GREEN** — `/efflux-executing` runs `bun run typecheck` centrally after each wave and fixes failures before the next — so decompose by *what typechecks together*, NOT by dependency layer: changes that only compile as a set must share one wave. The trap is an `HttpApi` addition, which is a typecheck cycle — adding an `HttpApiGroup` to the contract makes `HttpApiBuilder.layer` require its handler, so the group + its handler + the handler's registration in `index.ts` must land in the SAME wave; likewise, giving a tool a new binding dependency requires the root `Layer.succeed` provide + EVERY ambient `R`/`Context.Context` widening (`handlers.ts`, the turn drivers, `index.ts`'s `toWebHandlerWith` unions) in that SAME wave. Same-wave sibling imports between such tasks are fine — pin each file's exports in the task bodies; the central typecheck runs only after all a wave's agents finish. A layer-by-dependency split (contract → service → handler → wiring) leaves the tree red between waves and stalls `/efflux-executing`.
- **Landmines:** `ISSUES.md` at repo root is the authority — consult it before planning anything that touches Worker boot, secrets, DO RPC boundaries, containers, or the tool loop.
- **Effect v4 beta (`4.0.0-beta.94`):** never specify Effect APIs from memory, and never via the `effect-agent` subagent (it reads a machine-global, unpinned checkout). Authority order: this codebase's existing usage → the pinned `.claude/effect-smol` submodule (`packages/effect/src` — core incl. `unstable/http`, `unstable/httpapi`; init once with `git submodule update --init .claude/effect-smol`) → Context7 MCP. The submodule ships what the published package strips: search its `packages/**/test/**/*.ts` (globs recorded in `.claude/subrepos.json`) for real usage examples and core-team design notes when specifying an unfamiliar API. Scope "existing usage" greps to `apps/ packages/` — the submodule adds thousands of `.ts` files that would otherwise dominate results; reach into `.claude/effect-smol` deliberately, as step 2. **Before the plan commits to HAND-ROLLING a pure, standard utility — a cron parser, semver, glob, date math, a common config/format parser — grep the submodule + `node_modules/effect/src` for an existing MODULE that already provides the whole capability** (`effect` ships `Cron` — `Cron.parse`/`Cron.next`/`Cron.match` — plus many others). Decide hand-roll-vs-reuse CONSCIOUSLY at planning: a legitimate hand-roll is fine (effect's `Cron` has no `@daily` macros and unbounded impossible-date search — real reasons to hand-roll a bounded one), but the trade-off belongs in the plan, not discovered at code review. This authority-check is about whole existing MODULES you might be reinventing, distinct from the API-signature check above (which is about not inventing the shape of something you're already using). (full-cron-scheduling #102: a ~200-line hand-rolled cron parser shipped before the xhigh review pointed out `effect` already ships `Cron`; the hand-roll was kept for macro + bounded-horizon reasons, but that decision should have been made at planning.)

- **The PLATFORM ships capabilities natively too — check Cloudflare's bindings before treating a transport/feature as an external dependency, ESPECIALLY before framing a user-facing scope/cost question around it.** The MODULE-reuse check above is for pure utilities (`effect` ships `Cron`); its platform analog is that Cloudflare Workers provides native bindings for whole capabilities a plan might otherwise reach an external SaaS for — `send_email` (Email Service / Email Routing: real send from a Worker; `remote:true` sends actual email under `wrangler dev`), Queues, Workflows, Cron Triggers, D1/KV/R2/DO. Research the native path for each channel/feature the issue names DURING research (Context7 `/cloudflare/cloudflare-docs`), not after. This bites hardest when the plan is about to put a cost/scope fork to the USER premised on an external dependency ("email needs a Resend account + verified domain + an API key + can't be tested locally"): if a native binding collapses that cost, the question has a FALSE PREMISE — it gets rejected and can mis-anchor the whole design toward the heavier path. Confirm no native binding removes the trade-off BEFORE putting the fork to the user (this is the research precondition for the "ask in plain observable-outcome language" rule below — a well-worded question with a wrong premise still wastes a round). (sched-outcome-notifications #137: the email channel was framed as Resend-heavyweight/not-locally-testable and offered against a generic webhook the user never wanted; the user rejected the `AskUserQuestion` outright and hand-typed "slack and email using CF emails, it's in beta but works perfectly" — Cloudflare's native `send_email` binding is non-remote-boot-safe and sends real email under `wrangler dev`, so email was neither heavy nor untestable.)
- **A NOVEL API is a hypothesis, not verified code — scratch-compile it at planning.** When a task introduces an Effect API pattern with NO existing usage in `apps/ packages/` to copy (a new `HttpApiMiddleware`, a fresh `unstable/*` surface), the code you inline from submodule tests is unproven: generic-inference and layer-wiring shapes routinely differ from the citation. Before drafting the plan around it, write a throwaway file and `bunx tsc --noEmit -p <tsconfig>`; paste the version that COMPILED, and flag the task "novel API — expect iteration at the wave typecheck." (best-practices-refactor #73: the auth `HttpApiMiddleware` shipped two defects a 15-line compile would have caught — `error` type-param inference collapsing to `never` under the 2-arg `Service<Self, {requires}>` form, and `requires` being the router layer's build-time `RIn` not a per-request `R` — costing ~30 min of live debugging inside the wave.)

- **Once-per-operation instrumentation emitted from an Effect turn/loop driver is a LIFECYCLE decision, not "log at the end."** A side-effect placed after an `Effect.gen` for-loop — a metric, a log line, a notification — fires ONLY on the success path: a hop timeout or model error propagates out of the loop first and skips it, so exactly the FAILED operations you most want to observe emit nothing. Specify `Effect.ensuring` in the task body (it runs on success, failure, AND interrupt/disconnect). Also decide the SUSPENDED-then-resumed semantics: an operation that parks (awaiting approval) and later resumes as a SEPARATE driver invocation double-counts unless the park is guarded (a `parked` flag → skip the emit; the resume emits the single line). Point the DA at "does this fire on failure/interrupt, and does a parked-then-resumed op emit once or twice?" (core-metrics-console #141: the plan's "emit `logTurnMetric` when the hop loop finishes" shipped success-only + approval-park double-count + `/v1`-disconnect drop across all three turn drivers — the high-effort code review's single largest fix round, all resolved with `Effect.ensuring` + a `parked` guard.)

- **An HttpApiClient call whose PAYLOAD is a `Schema.Class` must be inlined as a CONSTRUCTED INSTANCE (`new X({…})` or a `makeX` helper), never a plain object literal.** The typed client's request encoder needs the class instance; a plain `{…}` matching the encoded shape TYPECHECKS (structural) but fails at RUNTIME with `Expected <ClassName>, got {…}` — typecheck-invisible, so it surfaces only at live-verify. This is exactly why `makePromptRequest` exists for `PromptRequest` (ISSUES.md). It applies to EVERY such payload — `PromptRequest`, `SubagentTaskRequest`, … — so when a task inlines more than one client call, apply it to ALL of them and point the devil's-advocate at any object-literal payload. (`Schema.Struct` payloads like `AgentConfig` are fine as plain objects — the trap is `Schema.Class` specifically.) (eval-harness #148: the plan used `makePromptRequest` for the `prompt` call but inlined a plain object for the `/tasks` judge call — the identical trap, missed on the second call, caught only at live-verify as one `fix` commit.)

- **Default to the HOUSE IDIOM for a cross-cutting concern; a custom helper needs a PROVEN reason, and a "the idiom won't work here" excuse must be scratch-compiled.** Before inlining a NEW helper for something the codebase already does pervasively — tracing a function, extracting an error message, formatting a value — grep how it's done today and default to that (`grep -rn "Effect.fn(" apps/api/src` shows `Effect.fn("name")(function*(){…})` IS the house way to trace a function: `loadOverlay`, `loadSkillBody`, `uploadKnowledge`, `listSkills`, …). If the plan justifies a custom approach by asserting the idiom "collapses types / won't typecheck in THIS position," that NEGATIVE claim is a hypothesis exactly like a novel API — write the 15-line `bunx tsc --noEmit` of the idiomatic form and confirm it BEFORE putting the excuse in the plan. An unproven "why-not-the-idiom" reason survives plan → execute → review untouched (a reviewer can "confirm the reasoning" about your helper without ever testing the alternative) and then gets overturned the instant the user asks "why didn't you just use X?" — a full post-PR refactor. (otel-console-tracing #128: the plan invented a `traceTool` wrapper for per-tool spans and justified it with "`Effect.fn` in the `Toolkit.toLayer({…})` value position collapses `params` to `unknown`" — a claim never scratch-compiled. It was false; a 15-line compile proved `Effect.fn` preserves the contextual `params` typing, and all 17 local tool handlers + the dynamic MCP handler were converted to `Effect.fn` — dropping the helper entirely — AFTER the PR opened.)

- **A NEGATIVE-EXISTENCE claim ("no house precedent / idiom / module for X") is a GREP, not an assertion — run it and cite the result before the claim enters the plan.** The sibling rules above cover "the idiom won't compile HERE" (scratch-compile it) and "does a module already provide this" (grep before hand-rolling); this is the third face: a plan sentence asserting the codebase LACKS something, used to justify a design shortcut. An unverified negative survives the devil's-advocate untouched — the DA verifies what the plan cites, and nobody greps for what the plan says isn't there — and then becomes the standing justification for a real defect. (cross-session-memory #144: the plan skipped length refinements on strings destined for EVERY future system prompt with "no house precedent for length caps; keeps schemas codec-clean" — false: `isMaxLength` checks sat at `Schemas.ts:45` and `:106` — and the uncapped-description hole shipped into the draft until the plan DA disproved the claim with three counter-cites.)

- **The same skepticism applies to a NOVEL MECHANISM the plan itself invents, not just an external library API.** A brand-new coordination convention with zero existing-codebase precedent (a marker syntax, a custom retry protocol, a bespoke state machine) is just as unproven as an unfamiliar Effect API — it just can't be caught by `tsc --noEmit`, because it will typecheck fine while still being behaviorally wrong. Flag it explicitly as "novel mechanism — needs live end-to-end proof with a real input before this is trusted," and make sure the plan's verification task actually exercises it with real data, not a synthetic/simplified stand-in. (feature-generating: a `{{NAME}}`-marker secret-export convention invented for that plan was flagged as fragile by BOTH the planning devil's-advocate and the post-execution code-review pass — independently, at different gates — and both times only the narrow complaint raised got patched rather than the design being reconsidered. It only broke as expected once live-tested with a real API key: a script written the natural way, with no special marker, silently never got its secret exported. **When the same PLAUSIBLE concern surfaces at two independent gates, treat that convergence as equivalent to CONFIRMED and reconsider the mechanism's design — not as two separate tickets to patch individually.**)

- **A feature that adds a SECOND caller to a mechanism previously driven by ONE serialized caller must analyze whether that mechanism's safety RELIED on the serialization.** A path invoked only by a single serialized driver — a DO `alarm()` (CF delivers one at a time), a cron tick, a queue consumer, one turn loop — can be correct with NO lock purely because it never overlapped itself. Adding a new manual/API/UI trigger to that same path introduces concurrency it never faced: two callers now race whatever shared, deterministically-keyed resource it touches (a per-entity container/DO id, a fixed temp path, a singleton handle). Grep the path's callers at planning; if it grows from one serialized caller to two, design the guard (an in-memory in-flight `Set`, a lock, an idempotency check) INTO the first draft and point the devil's-advocate at it — do NOT reason "it matches the existing caller's lock-free simplicity," because that caller was lock-free only BECAUSE it was serialized. **And when the contended resource is a single key that multiple callers WRITE — a fixed R2/DO object key, a snapshot tarball — prefer SERIALIZING the write critical section (a mutex, a per-DO promise-chain) over a flag-avoidance trick: a point-fix that dodges the ONE interleaving you reasoned about ("just don't consume the turn's dirty flag") closes only that direction and leaves the REVERSE interleaving open — a stale in-flight writer clobbering the fresh one on the shared key — which `tsc` can't see and only a code review or a live race surfaces. If concurrency on the same seam is raised at the devil's-advocate gate AND again at code review, that convergence means your remedy was INCOMPLETE (one direction), not that there are two separate bugs — the "same plausible concern at two independent gates = reconsider the design" principle applies to your own partial fix.** Distinct from the "generalizing a narrow behavior inherits hardcoded content" bullet below (that's UI copy/labels/defaults, not concurrency) and the "novel mechanism the plan invents" bullet above (a brand-new convention, not a second caller of an existing path). (run-now-scheduled-job #126: "run now" added a 2nd, concurrent caller to `#runScheduledJob` — previously `alarm()`-only — sharing the deterministic per-job `Runner` id `idFromName(${name}:${job.id})`; the first plan draft claimed no lock was needed "like the alarm path's lock-free simplicity," a false equivalence the devil's-advocate caught, and a `#runningJobs` in-flight guard was designed in before any code ran. Left unguarded, a manual run coinciding with the alarm fire would restore-over and tear down the other's container, spuriously failing a real scheduled run and multiplying billed containers.) (user-file-upload #146: user upload became a 2nd concurrent writer of the per-session `workspaces/<name>.tar.gz` R2 key alongside the turn-end `snapshotIfDirty`; the DA flagged the seam's concurrency, and the plan's remedy — force-snapshot WITHOUT touching `#DIRTY_KEY` — closed the "turn's writes get dropped" direction but left a stale concurrent turn-snapshot free to clobber the just-uploaded file (last-write-wins on the shared key). Code review caught the reverse race; the real fix serialized EVERY tar+PUT behind a per-DO `#snapshotChain` so whichever snapshot runs last re-tars the live container and wins with complete state — the point-fix should have been a serialization from the first draft.)

- **A NEW fetch on the hot path of EVERY turn must state its FAILURE MODE and degrade posture in the plan — and one bound gets ONE unit across every layer that enforces it.** Adding a per-turn load (an index, a hint, a config read) from a store the turn didn't previously touch changes the turn's failure domain: an `Effect.promise` rejection is an unrecoverable DEFECT, so an unstated failure mode defaults to "a hiccup in that store 500s every session that depends on it." If the payload is optional/nice-to-have, the plan must SPECIFY best-effort degrade (tapCause-log → skip, the Registry-writes precedent) in the task body — reviewers can reverse an explicit posture, but silence ships the SPOF. Two adjacent traps from the same run: (a) don't route the fetch through a second DO for wiring symmetry when the Worker root already holds the binding (a needless serialized double hop on every turn); (b) when the same bound is enforced at two layers (schema check + store check), name the UNIT once — a byte cap under a char-counting `isMaxLength` schema is a self-contradiction no wave gate can see, rejecting multibyte input that passed every documented limit. (cross-session-memory #144: the memory-index load shipped as a hard every-turn dependency via an Agent-DO proxy hop with byte caps under char schemas; all three were top-half code-review findings, fixed as one best-effort one-hop `loadMemoryIndex` + character caps end-to-end.)

- **An INHERITED convention — a default rule, an auto-remap, a bypass — must be RE-DERIVED when a new tool's side-effect CLASS is wider than the tools the convention was built for.** The destructive-exemplar lesson below says confirm/undo affordances don't transfer; this is its policy-level sibling: approval/bypass conventions don't transfer either. A convention like "the `/v1` facade remaps `ask`→`allow` because it can't park approvals" was derived for SESSION-SCOPED, recoverable side effects (a sandboxed Bash call); inheriting it for a tool whose side effect is DURABLE and CROSS-SESSION (a memory write that lands in every future session's system prompt) silently defeats the very protection the tool's `ask` default was added for. When the plan lists an inherited convention as a BENEFIT ("the remap keeps unattended flows working"), that is the tell to stop and re-derive: does the convention's premise still hold for this side-effect class, or must it fail CLOSED here? Point the devil's-advocate at every inherited default/remap/bypass a new tool flows through. (cross-session-memory #144: the plan AND its DA endorsed the inherited remap; the high-effort review ranked it the single most severe finding, fixed as `ask`→`deny` for `memory_write`/`memory_delete` on the facade.)

- **A type that CROSSES the DO RPC fence must be derived with `Pick`, not `typeof X.Encoded`.** When a task narrows a DO-method return (or a per-turn service type fed from one) to a schema-derived plain type, `typeof SomeSchemaClass.Encoded` does NOT survive Cloudflare's DO-stub type transform — the opaque `ReadonlySide<Schema.Literals<…>>` widens back to `string` and reds the wave typecheck (see ISSUES.md "`Schema.Class` cannot cross a Cloudflare Durable Object RPC boundary"). Inline `Pick<SomeSchemaClass, "field" | …>` instead — it stays schema-derived (no re-listed literals) and survives the fence. A passing sibling that uses `typeof X.Encoded` is NOT proof it's fence-safe — it may compile only because its consumer takes a plain union. (prev1-quality-refactor #90: `PlainTodo = typeof TodoItem.Encoded` reddened wave 2 on `TodoStore.read`/`latestTodos`; `Pick<TodoItem, "content" | "status">` fixed it, after the devil's-advocate wrongly cleared the encoded form by checking only that the impl yields literals.) **A DISCRIMINATED-UNION DO-method return (`{a}|{b}`) crosses the fence badly in a second, distinct way:** the stub transform turns it into a union-of-Promises (`(Promise<{a}&Disposable>&Pick<…>) | (Promise<{b}&Disposable>&Pick<…>)`) that TS will NOT collapse into a single `PromiseLike` at the provider layer's `Effect.promise(() => stub.method())` site — it infers the first arm only and reds on the second. Give `Effect.promise` an explicit type arg — `Effect.promise<{a}|{b}>(() => stub.method())` — and co-locate that provider-layer edit in the SAME wave as the DO method + the service type (three restatements of the union → extract one shared `type` and reference it in all three). A plan that flags the provider layer "verify-no-edit" because the INPUT types match will still red on the RETURN union. (full-cron-scheduling #102: `createScheduledJob`'s `{id,nextRunAt}|{error}` return reddened the wave-2 central typecheck at `AgentLoop.ts`'s `makeScheduledJobsLayer`; the plan predicted no edit for the wrong reason. See the matching ISSUES.md landmine.)

## Process

0. **Re-sync `origin/staging` first.** `git fetch origin staging`; if the main checkout is behind, re-sync it before drafting. `/efflux-planning` runs from the MAIN checkout's working tree (NOT a worktree), and the `efflux-*` skills evolve fast on `staging` — every postmortem tightens them — so a behind-`staging` checkout silently plans against stale guidance. (openai-facade #68 was authored from a `#63` checkout missing #64's wave-boundary-clean rule and `efflux-verifying`'s clobber/405 signatures, and reproduced BOTH already-forbidden anti-patterns: a red wave-1 typecheck from splitting a contract off its handler, and a slow deploy-clobber diagnosis.)
1. **Research.** Codebase first — copy the local convention and cite `file:line` for every pattern a task relies on. Read `ISSUES.md` for landmines touching the plan's surface. Effect v4 APIs only from source, in the authority order above.

   **Impact-grep a widened shared type across ALL SIX typecheck roots.** When a task adds a member to a shared type that is *exhaustively matched* — a new `Schema.Union` member, a new discriminated-union `_tag` — grep its consumers across `apps/ packages/ scripts/` (the full typecheck set, incl. `apps/tui` and `apps/api/container`), NOT just `apps/ packages/`. That narrower scope is only for Effect-API-*usage* greps (which dodge submodule noise); a contract's blast radius is every exhaustive match of it, anywhere `bun run typecheck` compiles. Two break shapes must be co-located with the widening in the SAME wave: (a) field access on a member that lacks the field — TS2339, e.g. `.turn` on a turn-less member (a `.tsx` timeline); and (b) a **value-returning** `switch(x._tag)` with no `default` that goes non-total — TS2366 "lacks ending return", easy to miss because it's a different shape than (a) and often lives in a `scripts/` CLI, not `apps/`. (compaction-todo #76: a `scripts/agent.ts` formatter switch was missed by an `apps/`-scoped grep and reddened the wave-1 central typecheck.)

   **When a fact you DERIVE from code contradicts an existing docstring or comment, RE-TRACE your reading before declaring the doc wrong — the doc is usually right.** Especially for an interpolated path/key/format string: trace every `${var}` to its BINDING, don't read the literal template. (eval-harness #148: the plan asserted the archive key `archives/${name}/${closedAt}/…` "omits `id`" and explicitly called the correct `Journal.ts`/`Agent.ts` docstrings wrong — but `name` there is `this.ctx.id.name`, the FULL DO name `<name>/<id>`, so the real key is the 3-segment `archives/<name>/<id>/<closedAt>` the docstrings stated. The devil's-advocate caught it pre-code, but a confident-but-wrong fact still burns a review cycle.)

   **A new tool's `needsApproval` must be checked against EVERY driver that resolves approvals, not just the primary one.** This codebase has more than one turn driver that can resolve a parked tool call — the interactive SSE/prompt path (`PromptTurn.ts`/`StreamingTurn.ts`) and the OpenAI-compatible `/v1` facade (`OpenAiHandlers.ts`, whose `autoApproveRules` remaps `ask`→`allow` because that facade can never resume a parked turn). A tool that hardcodes `needsApproval: () => Effect.succeed(true)` instead of routing through `ApprovalRules`/`DEFAULT_TOOL_RULES` bypasses that remap and silently breaks on `/v1` — grep every approval-resolving driver during research, not just the one the plan's main flow exercises. (feature-generating #98: `request_secret`/`create_scheduled_job` shipped hardcoded, caught only by post-execution code review.)

   **A change to a TOOL's name or parameters has consumers OUTSIDE the six typecheck roots — the model-facing prose that tells the model how to call it.** Skill `.md` files (`apps/api/skills/`), docs, and the tool's own `description` string instruct the model to call the tool with specific params; they are pure runtime prompt text, so `tsc` never sees them and a stale skill silently makes the model call the tool with removed/renamed params on the exact flow it drives. When a task renames a tool or changes its parameter shape, grep the BARE tool name across `apps/api/skills/` and docs (NOT `.ts`-scoped), and scope the skill/doc edit into the SAME plan — it is a first-class consumer, invisible to the wave typecheck.
