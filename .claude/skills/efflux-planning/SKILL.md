# efflux-planning

Produce a wave-structured plan that `/efflux-executing` runs. The stack is fixed and known — do NOT run a detection dance (no probing for lint configs, test runners, or package managers). Bake decisions on the facts below and spend the planning budget on the actual task.

This is v1 of the skill — deliberately lean. It gets sharpened by `/efflux-postmortem` findings over future PRs.

## Stack (fixed)

- **Runtime/PM:** Bun workspaces — `apps/api` (Cloudflare Worker: HttpApi + `Agent` DO-per-session + Container sandbox), `apps/web` (Vite + React chat FE), `packages/shared` (HttpApi contract + schemas; all types flow from Effect Schemas).
- **Verify:** `bun run typecheck` (chains `bun run cf-typegen` first, regenerating the gitignored `worker-configuration.d.ts`, then the three tsconfigs), `bun run build`. `bun run test` (root vitest) and `bun run lint` (`biome check .`) ALSO exist and are CI-gated (`.github/workflows/ci.yml`: typecheck + test + lint, `--frozen-lockfile`). The `/efflux-executing` wave gate is typecheck-ONLY, so every plan MUST carry a pre-PR step that runs `bun run lint` + `bun run test` from the worktree (and commits an updated `bun.lock` on any dep change) — else the PR reds in CI while the waves looked green. **FE/tooling gotchas:** biome lints `apps/**`, so generated shadcn `components/ui/*` must be added to `biome.json` `files.includes` as `!` negations (they ship `!`/`as`), Tailwind-v4 CSS (`@theme`/`@apply`/`@custom-variant`) must be excluded from biome's CSS parser (add a `!<file>.css` negation), and inline `<script>` in `index.html` IS linted (use `const` + optional `catch`, never `var`). Any skill/agent file a plan creates must be committed on the plan's branch — files authored in the main checkout do not self-track into the worktree.
- **Deploy:** `bun run deploy` — ALWAYS the package script, never bare `wrangler deploy`: only the script fires the `predeploy` hook (FE build + skills upload), so the bare form can ship a stale `apps/web/dist`. Requires a local Docker daemon (container image). Local dev: `bun run dev` (also needs Docker). Logs: `bun run tail`. Treat the repo `CLAUDE.md` "Commands" section as the command authority. **Any task that verifies a FE surface locally MUST bake in two worktree gotchas (full detail in `/efflux-verifying`):** build `apps/web/dist` with `.dev.vars` sourced (`set -a; . .dev.vars; set +a; bun run build`) so `VITE_API_TOKEN` is inlined — a plain `bun run build` ships an empty token and every panel 401s; and start `wrangler dev` via the worktree's OWN `node_modules/.bin/wrangler --config <abs>/wrangler.jsonc` on free ports, never `bunx wrangler` (which can silently serve a SIBLING worktree's code, so new routes 404 and edits don't take effect).
- **Live smoke CLI:** `bun scripts/agent.ts <name> <id> --message "hi" [--url <worker-url>] [--model M] [--skill S] [--role R]` (or `BASE_URL` env).
- **Demo model pin:** any plan step that exercises the toolkit live (a tool loop) MUST pin `--model openai/gpt-4o-mini`. Never `openai/gpt-5.2` — it 400s the whole toolkit with a strict-schema error (ALL tools, not just new ones; the README uses gpt-5.2 only on the toolkit-free `/tasks` surface). Never rely on the free default `tencent/hy3:free`, which flakes at tool choice.
- **Conventions:** feature PRs target `staging` and use `Refs #N` (issues close only via `/efflux-releasing`'s staging→main promotion PR, which carries the `Closes #N` lines); merge commits only (never rebase/squash); never `--no-verify`; no `as` casts or `!` assertions; schema-first — types flow from Effect Schemas; verification means exercising a running worker, not typecheck/build alone — but LOCAL (`bun run dev`) is the default per `/efflux-verifying`, with the shared deployed worker reserved for a single final pre-PR pass (every deploy is real, billed Container usage). Code style: **JSDoc on declarations only — no inline `//` comments** (self-documenting code; fold only critical invariants into a declaration's JSDoc — ISSUES.md holds the deep gotchas); **files stay single-purpose** — split a new driver/subsystem into its own module rather than growing a file past ~400 lines. Inlined code shapes in task bodies MUST follow this (JSDoc-only, no `//`) so agents reproduce the house style.
- **Plans dir:** `~/c0de/plans/efflux/`.
- **Execution model:** `/efflux-executing` runs the plan in an isolated worktree (`.claude/worktrees/<plan-name>`, branched from `origin/staging`) and spawns each wave's tasks as PARALLEL `efflux-task-executor` agents. Consequences for the plan: the `> **Branch:**` metadata line is REQUIRED (optionally `> **Base:**` when the work builds on an open PR branch instead of `staging`); no two tasks in the same wave may touch the same file (they run concurrently); and each task body must be SELF-CONTAINED — sub-agents reliably read their prompt but unreliably read referenced files, so inline any binding pattern or `**Do not:**` list into the task body rather than pointing at another document. **Every wave must also end GREEN** — `/efflux-executing` runs `bun run typecheck` centrally after each wave and fixes failures before the next — so decompose by *what typechecks together*, NOT by dependency layer: changes that only compile as a set must share one wave. The trap is an `HttpApi` addition, which is a typecheck cycle — adding an `HttpApiGroup` to the contract makes `HttpApiBuilder.layer` require its handler, so the group + its handler + the handler's registration in `index.ts` must land in the SAME wave; likewise, giving a tool a new binding dependency requires the root `Layer.succeed` provide + EVERY ambient `R`/`Context.Context` widening (`handlers.ts`, the turn drivers, `index.ts`'s `toWebHandlerWith` unions) in that SAME wave. Same-wave sibling imports between such tasks are fine — pin each file's exports in the task bodies; the central typecheck runs only after all a wave's agents finish. A layer-by-dependency split (contract → service → handler → wiring) leaves the tree red between waves and stalls `/efflux-executing`.
- **Landmines:** `ISSUES.md` at repo root is the authority — consult it before planning anything that touches Worker boot, secrets, DO RPC boundaries, containers, or the tool loop.
- **Effect v4 beta (`4.0.0-beta.94`):** never specify Effect APIs from memory, and never via the `effect-agent` subagent (it reads a machine-global, unpinned checkout). Authority order: this codebase's existing usage → the pinned `.claude/effect-smol` submodule (`packages/effect/src` — core incl. `unstable/http`, `unstable/httpapi`; init once with `git submodule update --init .claude/effect-smol`) → Context7 MCP. The submodule ships what the published package strips: search its `packages/**/test/**/*.ts` (globs recorded in `.claude/subrepos.json`) for real usage examples and core-team design notes when specifying an unfamiliar API. Scope "existing usage" greps to `apps/ packages/` — the submodule adds thousands of `.ts` files that would otherwise dominate results; reach into `.claude/effect-smol` deliberately, as step 2.
- **A NOVEL API is a hypothesis, not verified code — scratch-compile it at planning.** When a task introduces an Effect API pattern with NO existing usage in `apps/ packages/` to copy (a new `HttpApiMiddleware`, a fresh `unstable/*` surface), the code you inline from submodule tests is unproven: generic-inference and layer-wiring shapes routinely differ from the citation. Before drafting the plan around it, write a throwaway file and `bunx tsc --noEmit -p <tsconfig>`; paste the version that COMPILED, and flag the task "novel API — expect iteration at the wave typecheck." (best-practices-refactor #73: the auth `HttpApiMiddleware` shipped two defects a 15-line compile would have caught — `error` type-param inference collapsing to `never` under the 2-arg `Service<Self, {requires}>` form, and `requires` being the router layer's build-time `RIn` not a per-request `R` — costing ~30 min of live debugging inside the wave.)

- **The same skepticism applies to a NOVEL MECHANISM the plan itself invents, not just an external library API.** A brand-new coordination convention with zero existing-codebase precedent (a marker syntax, a custom retry protocol, a bespoke state machine) is just as unproven as an unfamiliar Effect API — it just can't be caught by `tsc --noEmit`, because it will typecheck fine while still being behaviorally wrong. Flag it explicitly as "novel mechanism — needs live end-to-end proof with a real input before this is trusted," and make sure the plan's verification task actually exercises it with real data, not a synthetic/simplified stand-in. (feature-generating: a `{{NAME}}`-marker secret-export convention invented for that plan was flagged as fragile by BOTH the planning devil's-advocate and the post-execution code-review pass — independently, at different gates — and both times only the narrow complaint raised got patched rather than the design being reconsidered. It only broke as expected once live-tested with a real API key: a script written the natural way, with no special marker, silently never got its secret exported. **When the same PLAUSIBLE concern surfaces at two independent gates, treat that convergence as equivalent to CONFIRMED and reconsider the mechanism's design — not as two separate tickets to patch individually.**)

- **A type that CROSSES the DO RPC fence must be derived with `Pick`, not `typeof X.Encoded`.** When a task narrows a DO-method return (or a per-turn service type fed from one) to a schema-derived plain type, `typeof SomeSchemaClass.Encoded` does NOT survive Cloudflare's DO-stub type transform — the opaque `ReadonlySide<Schema.Literals<…>>` widens back to `string` and reds the wave typecheck (see ISSUES.md "`Schema.Class` cannot cross a Cloudflare Durable Object RPC boundary"). Inline `Pick<SomeSchemaClass, "field" | …>` instead — it stays schema-derived (no re-listed literals) and survives the fence. A passing sibling that uses `typeof X.Encoded` is NOT proof it's fence-safe — it may compile only because its consumer takes a plain union. (prev1-quality-refactor #90: `PlainTodo = typeof TodoItem.Encoded` reddened wave 2 on `TodoStore.read`/`latestTodos`; `Pick<TodoItem, "content" | "status">` fixed it, after the devil's-advocate wrongly cleared the encoded form by checking only that the impl yields literals.)

## Process

0. **Re-sync `origin/staging` first.** `git fetch origin staging`; if the main checkout is behind, re-sync it before drafting. `/efflux-planning` runs from the MAIN checkout's working tree (NOT a worktree), and the `efflux-*` skills evolve fast on `staging` — every postmortem tightens them — so a behind-`staging` checkout silently plans against stale guidance. (openai-facade #68 was authored from a `#63` checkout missing #64's wave-boundary-clean rule and `efflux-verifying`'s clobber/405 signatures, and reproduced BOTH already-forbidden anti-patterns: a red wave-1 typecheck from splitting a contract off its handler, and a slow deploy-clobber diagnosis.)
1. **Research.** Codebase first — copy the local convention and cite `file:line` for every pattern a task relies on. Read `ISSUES.md` for landmines touching the plan's surface. Effect v4 APIs only from source, in the authority order above.

   **Impact-grep a widened shared type across ALL SIX typecheck roots.** When a task adds a member to a shared type that is *exhaustively matched* — a new `Schema.Union` member, a new discriminated-union `_tag` — grep its consumers across `apps/ packages/ scripts/` (the full typecheck set, incl. `apps/tui` and `apps/api/container`), NOT just `apps/ packages/`. That narrower scope is only for Effect-API-*usage* greps (which dodge submodule noise); a contract's blast radius is every exhaustive match of it, anywhere `bun run typecheck` compiles. Two break shapes must be co-located with the widening in the SAME wave: (a) field access on a member that lacks the field — TS2339, e.g. `.turn` on a turn-less member (a `.tsx` timeline); and (b) a **value-returning** `switch(x._tag)` with no `default` that goes non-total — TS2366 "lacks ending return", easy to miss because it's a different shape than (a) and often lives in a `scripts/` CLI, not `apps/`. (compaction-todo #76: a `scripts/agent.ts` formatter switch was missed by an `apps/`-scoped grep and reddened the wave-1 central typecheck.)

   **A new tool's `needsApproval` must be checked against EVERY driver that resolves approvals, not just the primary one.** This codebase has more than one turn driver that can resolve a parked tool call — the interactive SSE/prompt path (`PromptTurn.ts`/`StreamingTurn.ts`) and the OpenAI-compatible `/v1` facade (`OpenAiHandlers.ts`, whose `autoApproveRules` remaps `ask`→`allow` because that facade can never resume a parked turn). A tool that hardcodes `needsApproval: () => Effect.succeed(true)` instead of routing through `ApprovalRules`/`DEFAULT_TOOL_RULES` bypasses that remap and silently breaks on `/v1` — grep every approval-resolving driver during research, not just the one the plan's main flow exercises. (feature-generating #98: `request_secret`/`create_scheduled_job` shipped hardcoded, caught only by post-execution code review.)

   **A find-all-references / rename / eradication sweep must be COMPLETE and UN-FILTERED.** When a task must remove or exhaustively locate a term (a rename, a "zero legacy references" goal): (1) grep the BARE term — never pipe through `grep -v <newname>`; if the new name doesn't contain the old substring (`efflux` has no `flue`), that filter only HIDES true positives sharing a line (`Project-local to effect-flue/efflux`). (2) Use `grep -rnI` (or `git grep --untracked`), NOT plain `git grep` — files authored in the main checkout aren't tracked yet, so `git grep` can't see them (a whole untracked skill survived a rename this way). (3) Do NOT exclude lockfiles — `bun install` keeps the root workspace `name` on a package rename, so re-grep `bun.lock` AFTER `bun install`. Prove the count is 0 with the bare command; a "zero" claimed from a self-filtered grep is not zero. (docs-1.0.0 #88: `flue` was declared eliminated three times — the untracked `efflux-branding` skill, then its name-story line hidden by `grep -v efflux`, then `bun.lock` — before it was actually gone.)
2. **Exemplar inventory.** If the issue or user cites a template ("like <existing setup X>"), enumerate X's FULL inventory during research and list every element you're omitting in the plan for the user to see. Silent scope cuts against a named exemplar are the #1 "that's not what I asked" rework source (a releasing skill was silently dropped from the skills-suite plan this way).

   **Adopting a tool (linter/formatter) is exemplar-inventory too — and a fork.** When the plan borrows a linter/formatter from another repo (biome from vitaal), copying its config blind fails on an EXISTING, unformatted codebase: (a) decide reformat-EVERYTHING vs linter-only UP FRONT — a formatter enabled on non-conformant code either churns all 100+ files (obscuring the real diff) or must be scoped off; (b) derive the config from THIS codebase's actual style (grep the indent — tabs vs spaces — before setting `indentStyle`), never inherit the exemplar's; (c) exclude static-asset dirs and non-source globs (`public/`, `**/*.svg`) — a linter that scans image assets fails on the first one. (best-practices-refactor #73: biome copied vitaal's tab-indent onto a 2-space codebase → two config-churn cycles at the pre-PR lint gate, then a favicon `.svg` red-CI'd on `noSvgWithoutTitle`.)

   **Ask the user in plain, observable-outcome language — never implementation jargon.** Any `AskUserQuestion` put to the USER (not a subagent) to resolve a fork must be phrased as what they will SEE or be able to DO — never via schema/union names, Effect API names (`ctx.waitUntil`), or queue/transport mechanics. Lead each option with a one-line plain statement of what the choice changes for them, and state a scope option's observable behavior AND its limits, not just the mechanism's name. If a question can't be asked without a type or API identifier, it's aimed at the wrong audience — reframe it (or ask a subagent instead). (stream-reattach #81: the first architecture-fork question, framed in "frame source / journal granularity / `ctx.waitUntil`" terms, was rejected outright — "i don't understand the question" — costing a full re-ask in plain English.)
3. **Tracker check.** `gh issue list --state all --search "<surface>"` and `gh pr list --state all --search "<surface>"` — look for twins and in-flight work before drafting tasks.
4. **Draft.** Use the plan template: a `# Plan:` header with `> **Status:** DRAFT` and `> **Branch:**` lines, then waves of tasks, each task with `**Files:**` and `**Acceptance:**`. No two tasks in the same wave may touch the same file — waves must be file-disjoint because `/efflux-executing` runs a wave's tasks as parallel agents sharing one worktree. **Also: every wave boundary must be typecheck-clean** — `/efflux-executing` runs a central `bun run typecheck` after each wave and blocks on failure, so a change that leaves a CONSUMER non-compiling until its counterpart lands must sit in the SAME wave as that consumer (file-disjoint tasks in one wave still run in parallel). The classic traps: adding contract endpoints makes `HttpApiBuilder.group` non-total until the matching handlers land (co-locate the contract task with the handler task); adding a REQUIRED argument to a shared function breaks every call-site until they pass it (co-locate the signature change with the call-site edits); **adding a `query` (or `payload`) schema to an EXISTING endpoint makes the typed `HttpApiClient` request's `query` property REQUIRED even when every field is `Schema.optionalKey`** — so every existing caller (`client.<group>.<op>({ params })` in `apps/tui`, `apps/web`) must add `query: {}` in the SAME wave, or the central typecheck reds. Do NOT plan an `optionalKey` query as a zero-caller-impact addition; it is not (session-lifecycle #77: the `mode` query on `reset` broke the TUI `agents.reset` call — the plan and its devil's-advocate both wrongly claimed "no caller edit needed"). Sequence the earlier waves as standalone compile-clean ADDITIONS, and land the interface + its consumers together in one later file-disjoint wave.

   **A new `packages/shared/src/*.ts` module needs its `index.ts` barrel-export line in the SAME task that creates it.** Every existing module is re-exported from `packages/shared/src/index.ts` (`export * from "./X.ts"`) — a plan that adds a new schema/contract module without also adding its barrel line breaks every `@efflux/shared` import of it until someone notices at the wave typecheck. Check this explicitly when scoping a task that creates a new `packages/shared` file. (feature-generating #98: `Secrets.ts`/`Schedule.ts` shipped without their barrel lines, caught by live typecheck diagnostics mid-wave rather than planned for.)

   **Hoist shared code into the foundation wave.** Before waving up tasks, list the utilities, hooks, and coordination state that MORE THAN ONE task will need — error/message extractors, formatters, validation predicates, shared reactive atoms (a version-bump/refresh signal, a selected-X atom). Create each ONCE in the earliest wave and have later tasks import it; never let N parallel tasks each reimplement it. Two smells that mean "hoist this now": (1) two task bodies would carry the same instruction ("surface errors inline like Chat.tsx", "validate the name") — that shared sentence names a shared module; (2) a shared MECHANISM (e.g. a bump-counter one task writes and others react to) — the plan must spell out the contract for EVERY consumer, not just one, or the unspecified consumer silently half-wires it. (showcase-ui #67 shipped 4 copies of an error helper and a refresh atom wired into only 1 of its 2 consumers — both surfaced as review rework rippling across 7 files and adding 2 unplanned shared modules.)

   **Cross-cutting gotchas go in the shared block, not one task.** When the plan introduces a convention new to the codebase (a styling approach, a new library, a config pattern), put its known TS/tooling gotchas in the plan's shared conventions/architecture block that EVERY task inherits — never bury them in a single task body. (showcase-ui #67 introduced CSS Modules but noted the `noUncheckedIndexedAccess` gotcha — `styles.foo` is `string | undefined`, coalesce with `?? ""`, never `as`/`!` — in the layout task only; a different task hit it and broke the wave typecheck.)

   **Testable exports from a CLI/entry module need an entry guard.** When a task exports pure functions from a module that ALSO runs side-effects at top level — a CLI that parses `process.argv`, calls `process.exit`, or makes network calls — so a sibling test task can import them, the plan MUST specify guarding the entry (`if (import.meta.main) { … }`) in that SAME task. Otherwise the test's `import` fires the CLI (argv parse → `process.exit(1)`) and the whole test file dies. (best-practices-refactor #73: T9.2 exported `verify`/`formatEvent` for T9.3's tests but left the CLI body unguarded; the central `bun run test` caught it, at the cost of an extra fix-agent round.)

   **UI-scoped work needs a pinned, observable manual demo — not just a mechanism.** For any task adding user-visible/FE behavior, name in its `**Acceptance:**` the CONCRETE user action that exercises it in the running app (the exact click-path a human takes to SEE it work), and confirm that action reaches the new code through a real UI entry point — not only a debugger. If the only trigger is DevTools or curl, the scope is incomplete: either widen it to a real entry point, or state plainly in the plan that the value is API-level and the demo is curl (so nobody expects a UX story that isn't there). (stream-reattach #81: "also wire the web chat" shipped a transient-blip auto-reconnect reachable only via the DevTools Offline toggle, with NO reload/reopen-resume — so #49's headline "turns survive disconnect" is not observable through normal UX; the gap surfaced only when the user asked "is this something not testable using the UX?". Distinct from the silent-scope-cut lesson above: nothing was cut — the scoped behavior simply had no user-reachable trigger.)

   **Mirroring an exemplar for a DESTRUCTIVE action does NOT transfer its safety affordances — re-derive them from the new action's reversibility.** An exemplar (`ScheduledFeaturesPanel`, `SkillsPanel`) gives you layout, state-machine shape, and atom wiring for free — but a confirm/undo affordance (or its ABSENCE) is a function of what the action destroys, not of the exemplar. Before copying an exemplar's delete control, ask: is the new target as recoverable as the exemplar's? If the exemplar deletes something re-creatable (a schedulable job, an editable skill) but the new task deletes something UNRECOVERABLE (a write-only secret value with no read-back), the exemplar's no-confirm delete is WRONG to mirror — require a confirm, and NEVER encode "no confirm" as a `**Do not:**` (that ships the unsafe version as an instruction the executor faithfully obeys). Point the devil's-advocate pass at every destructive control specifically. (delete-rotate-secret #107: the plan's `**Do not:** add a delete-confirm dialog` blind-copied `ScheduledFeaturesPanel`'s no-confirm delete; a deleted secret value is unrecoverable while a scheduled job is re-creatable, so code review reversed it and a two-step Confirm/Cancel was added.)

   Save to `~/c0de/plans/efflux/<plan-name>.md`.
5. **Devil's-advocate pass.** Spawn a critical-review agent on the draft before presenting; fold in valid findings. Point it at the union-consumer check explicitly — "grep ALL SIX typecheck roots (`apps/ packages/ scripts/`) for exhaustive matches of any widened type, watching for BOTH `.field` access (TS2339) AND non-total value-`switch`es (TS2366)" — an `api AND web` framing alone misses `scripts/` consumers. **Also point it at any type that crosses a DO RPC fence** (a DO-method return, or a per-turn service type fed from one): the encoded type must SURVIVE the RPC transform, so verify the assignment compiles (not just that the impl produces the right runtime values) — checking the impl alone false-cleared exactly this in #90, where `typeof TodoItem.Encoded` widened to `string` across the fence.

   **When a finding corrects a bug PATTERN (not a single line), re-check every other place in the SAME task body that follows the same pattern — not just the one illustrated code block.** Fixing a design flaw in the worked example without sweeping sibling call sites in the same task leaves the pre-correction version shipping right next to the fixed one; the executor implements the task body faithfully either way, so an un-swept sibling reads as "the plan said to do this." (feature-generating #98: the devil's-advocate pass correctly split "record real activity" from "re-arm to the known deadline" in the alarm-scheduler methods, but the task body's OTHER bullet — `deleteScheduledJob`, listed separately from the worked example — still called the pre-correction method. Shipped as the single most severe finding in the next code-review pass: deleting the last scheduled job could arm a stale alarm deadline and immediately wipe the session.) After applying any devil's-advocate correction, grep the task body for every other reference to the corrected method/pattern before considering the finding resolved.
6. **Present.** Show a summary with wave/task counts and ask whether to run `/efflux-executing`.
